# 流量上报与服务器计费口径

Heki 向 XBoard 上报用户的上传和下载流量。用户上传、下载的方向，与服务器网卡的入站、出站不是同一套口径，不能直接把两者相加后的数值等同。

## Heki 上报什么

- 上传：用户通过代理向目标网站或服务发送的数据。
- 下载：目标网站或服务通过代理返回给用户的数据。
- Heki 按用户累计代理转发的数据字节，分别上报上传和下载，不是读取整台服务器的网卡计数。
- Heki 向 XBoard 上报原始流量，不预乘节点倍率；面板再按自己的倍率和计费规则计算套餐扣量。

## 为什么服务器双向统计可能接近两倍

以普通落地代理为例，客户端连接落地服务器，再由落地服务器连接目标网站：

```text
上传：客户端 → 落地服务器 → 目标网站
下载：目标网站 → 落地服务器 → 客户端
```

无论用户上传还是下载，同一份有效数据都会进入落地服务器一次，再从落地服务器发出一次。忽略协议开销和其他流量，在同一统计时间段内：

| 统计口径 | 与 Heki 上传＋下载的近似关系 |
|---|---|
| Heki 上报的用户流量合计 | 上传＋下载 |
| 落地服务器仅统计出站 | 接近 Heki 上传＋下载 |
| 落地服务器仅统计入站 | 接近 Heki 上传＋下载 |
| 落地服务器入站＋出站相加 | 接近 Heki 上传＋下载的两倍 |

因此，**商家仅按服务器出站计费时，Heki 上报量通常与该出站量接近，并不是它的一半**。商家把入站与出站相加时，Heki 上报量才可能接近这个双向合计的一半。

例如，用户上传 1 GB、下载 9 GB，忽略开销时：

- Heki 上报：上传 1 GB、下载 9 GB，合计 10 GB。
- 落地服务器：入站约 10 GB，出站约 10 GB，双向合计约 20 GB。
- 若面板按上传＋下载、节点倍率 2 倍扣费，套餐扣量约 20 GB；Heki 原始上报仍为 10 GB。

## 为什么实际数值不会完全相等

这些关系适用于普通落地转发模型，不是固定换算公式。核对账单时还需考虑：

- **协议和网络开销**：加密封装、握手、TCP/IP 或 QUIC 头、确认包、保活和重传等，会影响网卡或商家统计。
- **服务器其他流量**：系统更新、面板 API、监控、备份、扫描和其他服务流量，不一定属于 Heki 用户转发量。
- **统计周期与单位**：Heki 按周期批量上报；面板、监控和商家的统计区间、更新时间及 GB/GiB 单位可能不同。
- **网络拓扑与计费范围**：中转、多级代理、内网出口、多个网卡，以及容器网桥重复计数，都可能改变比较结果。应先确认商家统计的是公网出口、某张网卡，还是所有接口之和。
- **商家与面板规则**：出站单向计费、双向相加、取较大方向或 95 峰值带宽计费并不等价；面板也可能设置节点倍率或其他扣费规则。

建议先用同一时间段内的 **Heki 原始上传＋下载** 对比商家明确的流量口径，再单独核对面板倍率后的套餐扣量。若遇到流量未上报或延迟，参见 [遇到问题如何排查](other/troubleshoot.md)。

## 上报失败后的自动恢复

Heki 在发送流量前先持久化批次，按现有 `submit_interval`（或面板下发的上报间隔）周期自动处理失败和恢复，**不需要人工对账解锁或重启节点**。状态与在线 IP 上报继续按原有周期执行。

| 请求结果 | 自动处理 |
| --- | --- |
| 收到面板成功确认 | 删除待发送批次；本地状态写入失败时重试写入，不在当前进程内重复发送已经确认的流量 |
| 确认尚未建立请求连接，例如 DNS、拨号或连接前 TLS 失败 | 保留相同批次 ID 和内容，下一上报周期自动重试；重启后继续恢复 |
| 请求已经发出，但响应丢失、读取超时或返回错误，无法确认是否入账 | 对没有可靠去重保证的面板保留未确认量，不重复发送该批次；下一周期自动继续上报新流量 |
| 面板协议明确保证持久化批次去重 | 使用相同批次 ID 和原始内容自动重试，成功后继续后续批次 |

目前适配的 HekiV1、SSPanel、Metron、PPanel 和 XBoard 都不视为具有可依赖的持久化批次去重保证。请求携带 `batch_id` 或 `Idempotency-Key`，不等于面板一定会去重。Heki 也限制 HTTP 库因这些请求头自行重发流量 POST；每轮仅做一次流量提交，已有明确的接口/节点类型兼容回退除外。

**默认优先避免重复扣量。** 对“面板可能已入账，但成功响应丢失”的情况，单靠 Heki 无法确认结果，也不能根据用户总用量的变化推断某一节点某一批次是否入账。该批次可能少计，但不会为了补报这笔不确定流量而一直阻塞后续上报。

例如：第一批 100 MB 的请求结果不明，之后又产生 20 MB；Heki 保留前 100 MB 的未确认记录，下一周期自动上报后 20 MB，不会把两批合并成 120 MB 重发。若第一批根本没有建立请求连接，则仍自动补报原来的 100 MB，随后发送后续增量。

## 状态文件与升级兼容

状态文件通常位于 `ip_user_cache_save_dir`，文件名类似 `traffic-pending-node-1.json`。正常待发送批次和未确认量分开保存：`uncertain.data` 按用户汇总未确认的上传/下载，`batch_count` 记录批次数，`last_batch_id` 记录最近一批；日志保留各次失败的批次 ID。这些诊断数据不是待补报队列，不会因为重启被重新发送，也不表示面板一定漏记了这些流量。

同一用户的多次未确认量会合并，避免按失败次数无限堆积批次。历史状态里的 `reconcile_required` 批次在启动后的上报周期自动转入未确认汇总，后续流量继续处理，**无需执行 `traffic-reconcile`**。旧的离线命令保留兼容，但不是正常运行或升级的必要步骤，也不能用它重新发送已经转入汇总的历史数据。

该目录必须允许 Heki 创建、写入及替换状态文件。默认会跟随实例配置目录；多实例应各自使用独立目录。Docker 用户需将状态目录挂载到可写的持久化目录；如果主配置以只读方式挂载，请将 `ip_user_cache_save_dir` 指向另一个可写的持久化目录，例如：

```ini
ip_user_cache_save_dir=/var/lib/heki
```

Docker 同时挂载该目录：

```yaml
services:
  heki:
    volumes:
      - ./heki-state:/var/lib/heki
```

此要求与 `ip_user_cache_save_enable` 是否开启无关。运行用户需要有相应目录权限。

状态文件损坏、被另一进程占用或目录不可写，属于本地存储/部署故障。程序会记录错误并保护已有数据；自动处理网络不确定结果不等于绕过这些检查。运行中的写入失败会保留内存数据并在后续周期重试落盘。不要通过删除状态文件处理网络上报失败；升级后同时检查节点可连接和流量上报成功。

# BT 过滤

`forbidden_bit_torrent` 用于拦截经过 Heki、能够识别出 BitTorrent 特征的流量，默认开启。在主配置 `heki.conf` 中设置，修改后重启 Heki：

```ini
forbidden_bit_torrent=true
```

此项是全局配置，当前不支持节点 `[USER]` 覆盖，也不依赖 `detect_packet=true`。设置为 `false` 可关闭这项过滤；独立配置的审计或路由拒绝规则仍然生效。

## 识别范围

> 以下增强随 2026-10-31 的 v1.2.9 同版本重发提供；旧版 1.2.9 用户也需重新下载安装包或拉取镜像并重建容器。旧版本只在部分协议首包上检查，存在 UDP、Hy2/TUIC 链路及拆分握手漏拦。

增强后的检查位于各协议共用的应用出站层，覆盖直连、本机出口 IP 绑定及路由代理出站。VMess、VLESS（包括 Vision）、Trojan、SS/SS2022、SSR、AnyTLS、Hysteria2、TUIC、Naive、Mieru 通过这些出站接口转发的数据均接受检查。

| 流量 | 检查方式 |
|---|---|
| TCP 明文 BT 握手 | 识别 `BitTorrent protocol` 握手；支持握手拆分到多次写入 |
| 明文 HTTP tracker | 检查初始 GET 请求地址中的 `info_hash` 与 `peer_id` 参数 |
| DHT | 按 bencode 结构识别常见查询和响应 |
| UDP tracker | 识别 BEP 15 connect 请求 |
| uTP | 识别 BEP 29 SYN 建连报文 |

TCP 只检查连接开始处最多 4096 字节；确认不匹配后直接转发，不扫描整条下载流。只有疑似握手或未完整接收的 GET 请求地址会暂存等待后续字节。UDP 逐包检查，因此同一 UDP 会话先发送普通数据也不会跳过后续 BT 检查。

## 为什么开启后仍可能下载

- 客户端启用了 BT 协议加密（MSE/PE）：Heki 看到的是加密的应用数据，无法从明文握手识别。
- tracker 使用 HTTPS，或数据通过额外 VPN/加密隧道传输：内部特征不可见。
- 客户端只有部分流量走代理，例如 TCP 走节点、UDP/DHT/uTP 直连，或者下载程序使用了另一条出站。
- TCP 已判定放行后才出现 BT 内容、超出初始检查范围的请求，以及不符合当前识别特征的变种流量，不属于全流量深度检测范围。

Heki 能解开自身代理协议的外层加密，但不会解密 BT 客户端额外启用的协议加密。标准 uTP 的 SYN 仍可在建连阶段识别，即使后续 BT 数据启用了加密；加密的 TCP peer 连接则不能靠明文握手识别。HTTPS tracker 本身不可见，也不代表随后建立的明文 peer 连接会被放行。

拦截 DHT/tracker 可以减少发现 peer 的途径，但客户端仍可能使用缓存的 peer 地址或其他发现方式。客户端如果还能建立加密 TCP 连接，下载可能继续，不能把这项过滤理解成固定比例限速。仅靠这一开关无法保证 100% 禁用 BT，封锁常见 BT 端口也无法保证，因为 peer 可以使用任意端口。

## 排查建议

1. 确认运行的是包含增强改动的构建，并在主配置中启用后重启。
2. 确认下载程序的 TCP 和 UDP 都实际经过待测节点；测试时停止其他代理和直连出口，结合节点出口流量或抓包核实。
3. 使用有权下载的测试资源，先关闭 BT 协议加密，分别测试 TCP peer、DHT、UDP tracker 和 uTP；不要仅凭 tracker 页面仍显示连接成功判断过滤无效。
4. 再开启协议加密对比。若只有加密模式仍可下载，这是特征过滤的能力边界；可结合已知 tracker 域名/IP 拒绝规则、流量限制和运营策略减少滥用，但不能据此承诺完全封锁。

正常 HTTP、HTTPS、DNS、游戏 UDP 仍应可用；如果只有某个自定义应用异常，保留对应开关前后的最小复现信息以排查误判。
